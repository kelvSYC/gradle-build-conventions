# Agent Guidance

Shared Gradle build conventions, published to GitHub Packages under group `com.kelvsyc.internal`.

This file is the agent guidance for this repository and is written to be model-neutral; `CLAUDE.md` only imports it. Keep tool- or vendor-specific instructions out of it.

## Modules

- `catalog` — publishes the shared version catalog, defined in `gradle/libs.versions.toml`: Gradle's standard location, which Dependabot requires to open update PRs, and which Gradle also registers as this build's own `libs`
- `platform` — platform BOM
- `settings-plugin` — settings plugin wiring repositories, the shared catalog (plus the platform as `libs.conventions.platform`; consumers declare the dependency themselves), the default group and versionless plugin requests into consumer builds; plugin IDs `com.kelvsyc.internal.settings` and `com.kelvsyc.internal.semver`. Only versionless requests in exactly the `com.kelvsyc.internal` namespace get the shared version: consumers' own plugins in longer namespaces (e.g. `com.kelvsyc.internal.kotlin-tools.*`) must resolve as the consumer declares them.
- `publishing-plugin` — GitHub Packages publishing convention; plugin ID `com.kelvsyc.internal.github-publishing`. `check` depends on `verifyPomDependencyVersions`, which parses the generated POMs (`GenerateMavenPom` tasks, after the internal-platform stripping) and fails on versionless dependencies; it must not depend on `GenerateModuleMetadata`, which builds every publication artifact (module metadata lists their sizes and checksums), pulling documentation jars into `check`. `RequireDependencyVersions` stays a `doLast` of module metadata generation, guarding `publish` and anything only module metadata expresses.
- `kotlin-plugin` — Kotlin convention plugins: `com.kelvsyc.internal.kotlin-multiplatform-base`, `-library`, `-jvm`, `-js` and `-native` (the build host's native target only: each host publishes just its own), and `com.kelvsyc.internal.kotlin-jvm-library`, with the `kelvsycKotlin` extension holding the shared compatibility floors (language/API version, `coreLibrariesVersion`, JVM release, JDK toolchain, Node.js version). The compiler Kotlin version (the catalog's `kotlin`) and this build's version are generated into the plugin jar at build time, so the plugins read nothing from a consumer's catalog: the Kotlin Gradle plugin dependency is pinned to the catalog's `kotlin`, and the versionless Kotest coordinates the plugins add are versioned by the shared platform they also add. Every consumer's build script classpath carries this module's dependencies (Kotlin Gradle plugin, KSP, the Kotest Gradle plugin, the Dependency Analysis plugin), and the plugins fail a build where any `org.jetbrains.kotlin` artifact there differs from the Kotlin Gradle plugin version, so a dependency bump that raises one breaks every consumer; the functional tests apply the plugins and catch it first. `kotlin-multiplatform-library` and `kotlin-jvm-library` honour the public API validation switch (below).
- `kotlin-common` — no plugins: the helpers `kotlin-plugin` and `kotlin-gradle-plugin-conventions` share (the Dependency Analysis rules, the Kotlin toolchain checks, the public API validation switch, and `KotlinConventions`, the conventions version and compiler Kotlin generated into its jar), so that neither convention artifact puts the other's dependencies on consumers' build script classpaths. It applies `embedded-kotlin` rather than `kotlin-dsl`, which would bring `java-gradle-plugin` and warn about the missing plugin descriptors.
- `kotlin-gradle-plugin-conventions` — Gradle-plugin convention plugins for code that runs inside Gradle (gradle-tools' cores): `com.kelvsyc.internal.kotlin-gradle-library` (`java-library` and Kotlin JVM) and `com.kelvsyc.internal.kotlin-gradle-plugin` (`kotlin-dsl`, which brings `java-gradle-plugin`), with the `kelvsycGradle` extension exposing the read-only `tier` (`GradleTier`, from the `com.kelvsyc.gradle.minimumGradle` Gradle property of the build, read when the plugin is applied). The tier selects the `gradle-public-api` version and the Kotlin standard library and language version `main` compiles against, and the `org.gradle.plugin.api-version` attributes; `verifyGradleLinkage` checks `main` and its runtime classpath against the tier's Gradle. The tier table lives in `GradleTier`, so adding or dropping a tier is a release here. The `kotlin-dsl` plugin dependency is at the version the Gradle building this repository expects (`expectedKotlinDslPluginsVersion`, which follows the catalog's `gradle`), and `jspecify` is generated into the jar from the catalog. Both plugins honour the public API validation switch (below). Its functional tests run their fixtures on a JDK 21 Gradle daemon (`org.gradle.java.home`), as gradle-tools does.
- `dokka-plugin` — Dokka convention plugin, `com.kelvsyc.internal.dokka`: HTML documentation built by `assemble`, JDK and Kotlin standard library links, source links derived from the `origin` git remote and `HEAD` (through settings-plugin's remote parsing), and a Dokka Javadoc javadoc jar for `java` projects that are not Kotlin Multiplatform (for Kotlin Multiplatform, the `kotlin-multiplatform-jvm` convention decides after evaluation: Dokka Javadoc, applying `org.jetbrains.dokka-javadoc`, when every target is JVM or common, else the HTML, since Dokka's Javadoc format rejects other platforms; adding a non-JVM target switches the jar to HTML). The JDK link follows the Kotlin conventions' `jvmRelease` or `compileJava`'s release; it is set, not a convention, because Dokka sets it from the Java toolchain itself. Dokka's `dokka*` configurations are forced to the catalog's `jackson`, `jsoup` and `freemarker` versions, generated into the plugin jar at build time; check whether a Dokka upgrade still resolves vulnerable versions of them before dropping that forcing.
- `jacoco-plugin` — JaCoCo convention plugin, `com.kelvsyc.internal.jacoco`: applies Gradle's `jacoco` plugin at the catalog's `jacoco` version (generated into the plugin jar at build time; the `jacoco-agent` catalog entry exists so Dependabot maintains it) and, with the `java` plugin, requires the XML and HTML reports of `jacocoTestReport` and makes it depend on `test`. It adds no tasks, checks or thresholds, and nothing is wired into `check`.
- `kover-plugin` — Kover convention plugin, `com.kelvsyc.internal.kover`: applies the Kover Gradle plugin at the catalog's `kover` version (a dependency of the plugin module, so consumers need no version) and sets `reports.total.verify.onCheck = false`, because Kover otherwise adds `koverVerify` and `koverCachedVerify` to `check`. It adds no rules, filters or report wiring. Kover measures common and JVM source sets only, so JS and native code is not covered and a JS-only project gets empty reports. `koverFindJar` remains a prerequisite of the JVM test task.

## Consumer guidance: shared versus local convention plugins

Do not mix a repository-local convention plugin with the shared ones in only some of a composite's builds. Gradle shares the shared plugins' classloader only between builds whose plugin classpaths are identical, so a local plugin applied in some builds gives those builds their own copies of the Kotlin Gradle plugin, KSP, Dokka, the Dependency Analysis plugin and Kotest. In kotlin-tools this raised daemon metaspace by about 70 MiB. Move such a convention into the shared plugins (as `kotlin-multiplatform-native` was), or apply local plugins in every build of the composite.

## Consumer guidance: public API validation

Setting the Gradle property `com.kelvsyc.kotlin.abiValidation=true` turns on the Kotlin Gradle plugin's ABI validation in projects applying `kotlin-multiplatform-library`, `kotlin-jvm-library`, `kotlin-gradle-library` or `kotlin-gradle-plugin`; `false` or no property leaves it off, and any other value fails the build. The base and target plugins never turn it on. The property belongs to the build, so set it in the root `gradle.properties` of every build of a composite.

With it on, `check` runs `checkKotlinAbi`, which compares the public API with the reference dumps in the project's `api/` directory (`<project>.api` for JVM, `<project>.klib.api` for JS and other klib targets) and fails when they differ or are missing. Commit the dumps; record an intended change by running `./gradlew updateKotlinAbi` and committing the diff. The dumps hold `public` and `protected` declarations and `@PublishedApi internal` ones, not `internal` or `private` ones.

Projects with a Kotlin/Native target are skipped (an info-level message says so): the native convention declares only the build host's target, and the klib dump records its targets, so a dump written on one host would fail on the others. Declaring every native target on every host would lift this, and is not planned yet. The switch is off by default while consumers record their dumps; a later release will turn it on by default.

## Publishing

The root `build.gradle.kts` declares the single publishing repository, `GitHubPackages`, on every subproject that applies `maven-publish`. Never declare any other publishing repository: any extra repository joins the `publish` lifecycle, which must stay the GitHub Packages release path only. Tests consume artifacts through `publishToMavenLocal` instead.

Publishing credentials, here and in the `github-publishing` convention, are declared with `credentials(PasswordCredentials::class)`, so they come from the `GitHubPackagesUsername` and `GitHubPackagesPassword` Gradle properties (in CI, the `ORG_GRADLE_PROJECT_GitHubPackagesUsername`/`ORG_GRADLE_PROJECT_GitHubPackagesPassword` environment variables of the release workflow's publish step). Never set credentials explicitly (`credentials { username = ...; password = ... }`) on a publishing repository: Gradle then marks every publish task to it incompatible with the configuration cache and disables the cache for the whole run. Gradle resolves the properties only when the task graph has a task publishing to the repository, and fails before any task runs if one is missing; that is why the convention declares no credentials without a GitHub `origin`, so `requireGitHubOrigin` still reports the missing remote first. Resolution credentials (the settings plugin's `gpr.user`/`gpr.key`, else `GITHUB_ACTOR`/`GITHUB_TOKEN`) are separate and unaffected.

## Versioning and releases

Versions come from git tags via the semver settings plugin; on a tagged commit the version is the bare tag version. `.github/workflows/release.yml` runs on every push to `main` (skipped when only `.github/**`, `**/*.md` or `docs/**` changed), and releases the pushed commit in this order:

1. Reuse a `vMAJOR.MINOR.PATCH` tag already on the commit (for instance one pushed by hand), or else compute the next version from the latest such tag and create an annotated tag **locally only**.
2. Run `./gradlew check`, then `./gradlew publish` as a separate invocation (with the configuration cache, tasks of one invocation run in parallel, so `check publish` would not hold publishing back until every check passed). Semver reads the local tag, so the bare release version is published.
3. Push the tag, only if step 1 created it.

The tag is pushed last so that a failed check or publish never leaves a remote tag without artifacts. If only the tag push fails, the release is published but the tag is missing from the repository, and the next release would compute the same version and fail to publish it. Recover by pushing the tag by hand: `git tag -a vX.Y.Z -m "Release vX.Y.Z" <released commit>` and `git push origin vX.Y.Z`, with the version from the failed run's log. Re-running the workflow instead would try to publish the same version again.

Next-version rules:

- no tag yet: `v0.1.0`
- default: patch bump
- label `release:minor` on the merged PR: minor bump
- label `release:major` on the merged PR: major bump

The labels must exist in the GitHub repository. They are read from the PR that produced the pushed commit (`gh api repos/{repo}/commits/{sha}/pulls`). Releases are serialized by `concurrency: release`.

## Dependencies and Dependabot

- Dependency repositories are declared only in the root `settings.gradle.kts` (`dependencyResolutionManagement`), with `RepositoriesMode.FAIL_ON_PROJECT_REPOS` so projects cannot add their own. Dependabot reads repositories from there (and from root `allprojects`/`subprojects` blocks), never from repositories a plugin adds; anything declared elsewhere makes its catalog lookups miss.
- The catalog's `gradle` version is the Gradle version these conventions are built and tested with; consumers' wrappers follow it. The catalog's `kotlin` is the compiler Kotlin and must equal Gradle's embedded Kotlin. `checkToolchainVersions` (part of `check`) fails if the wrapper is not a stable Gradle release, if `gradle` differs from it, or if `kotlin` differs from the embedded Kotlin.
- Dependabot groups routine Gradle updates (minor and patch) into one PR, because every merge to `main` is a release that each consumer then picks up. For the same reason it proposes a library release only once it is 3 days old (`cooldown`), so a release that is pulled or quickly superseded never ships to consumers. Majors, pre-1.0 libraries (where a "minor" can break) and the Gradle wrapper get their own PRs; extend `exclude-patterns` in `.github/dependabot.yml` when another library proves unreliable about semver. To drop one dependency from a grouped PR, comment `@dependabot ignore <dependency> minor version` (or `major version`, or just the name) on it; `@dependabot unignore <dependency>` restores it. Most catalog entries are used only by consumers, so this repository's own tests do not exercise them; the canary (below) does.
- The grouped catalog PR (`catalog-minor-and-patch`) merges itself: `.github/workflows/dependabot-auto-merge.yml` enables GitHub auto-merge on it, so it merges once the required checks (`build` and every `canary (<consumer>)` job) pass, and the merge releases. Every other Dependabot PR (majors, the excluded libraries, the Gradle wrapper) waits for a person, except the GitHub Actions bumps described next. Auto-merge is enabled with the `CONVENTIONS_TOKEN` personal access token, stored in both the Dependabot and Actions secrets (a run started by Dependabot sees only the former, one started by a person pushing to the PR only the latter), because a merge made with `GITHUB_TOKEN` triggers no workflows and would not release. Adding a consumer to the canary means adding its `canary (<repository>)` check to the required checks.
- GitHub Actions are pinned to a full commit SHA with the full version as a trailing comment (`uses: actions/checkout@<sha> # v7.0.1`), which lets Dependabot classify an update as minor or patch. `.github/workflows/actions-bump.yml` enables auto-merge on a Dependabot Actions PR when the update is minor or patch and every bumped action is from `actions/*`, `github/*`, `dependabot/*`, `gradle/actions` or `anthropics/claude-code-action`, so the PR merges once the required checks pass. Major bumps and other actions stay manual. It uses the same `CONVENTIONS_TOKEN`, which must be allowed to merge workflow-file changes (a classic token needs the `workflow` scope; a fine-grained token needs Workflows read/write).
- Gradle updates run weekly, and patch updates of the AWS SDK BOMs (`software.amazon.awssdk:bom`, `aws.sdk.kotlin:bom`) are ignored: they release almost daily, and every merge here becomes a release and a bump in each consumer. Their minor updates still come through.
- A Gradle upgrade is one change: the wrapper, the catalog's `gradle`, and the catalog's `kotlin` when the new Gradle embeds a different Kotlin. Dependabot ignores standalone Kotlin Gradle plugin bumps for that reason. Its Gradle wrapper PRs change only the wrapper, so they fail `checkToolchainVersions` as opened: complete them in place by setting the catalog's `gradle` to the new version (and `kotlin` to the new embedded Kotlin, from the Gradle release notes) on the same branch.

## Canary

The canary jobs in `.github/workflows/build.yml` build each consumer that has migrated to these conventions against the change under test, so a change that breaks a consumer fails here rather than after release. The local composite action `.github/actions/canary` (shared by every canary job) publishes this repository to Maven Local, checks the consumer out, and runs `.github/scripts/canary.sh <consumer-dir> <version> [tasks…]`: the script points the consumer's single pin (`gradle-build-conventions` in its `gradle/libs.versions.toml`) at that version and runs the consumer's build with `.github/canary/maven-local.init.gradle.kts`, which adds Maven Local (restricted to the `com.kelvsyc.internal` groups) to every build's plugin and dependency repositories.

The consumers are kotlin-tools (`:check`), rifflet (`:check consumerCompatibilityTest`: its fixture builds rifflet on the oldest supported Kotlin and Java, so a change to the shared floors that would break old consumers fails here) and gradle-tools. kotlin-tools and rifflet are entries of the `canary` job's `matrix.consumer`. gradle-tools is sharded because its `:check` is CPU-bound and slow on one runner: its root build honours `-Pcheck.shard=<index>/<count>`, a deterministic split of its cores, and the `canary-gradle-tools-shard` job runs `:check -Pcheck.shard=<i>/4` as four parallel matrix entries (checks `canary (kelvSYC/gradle-tools 1/4)` to `4/4`). Each shard is started from JDK 21 via the action's `jdk` input, because its Gradle daemon must run on JDK 21. To change the shard count, change the matrix's `shard` entries (`"1/4"`, `"2/4"`, …) together. The `canary-gradle-tools` job, named `canary (kelvSYC/gradle-tools)`, aggregates the shards: it needs only the shard job, runs even when a shard failed, and fails unless every shard succeeded (a cancelled or skipped shard fails it too), so the required checks stay `canary (kelvSYC/kotlin-tools)`, `canary (kelvSYC/rifflet)` and `canary (kelvSYC/gradle-tools)`, and the per-shard checks need not be required. Every plugin this repository publishes must therefore stay at bytecode 21 or lower; the modules build with `jvmToolchain(21)`. To cover a newly migrated consumer, add it to the `canary` job's `matrix.consumer` list with the tasks its own CI uses to verify a change, then add its `canary (<repository>)` check to the required checks. To reproduce a canary failure locally: `./gradlew publishToMavenLocal`, take the version from `./gradlew -q properties --property version`, then run `canary.sh` against a scratch checkout of the consumer (it edits the consumer's catalog); for a gradle-tools shard pass `:check -Pcheck.shard=<i>/4` as the tasks.
